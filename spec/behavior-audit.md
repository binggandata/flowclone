# 功能效果级对比审计（FlowClone vs 原版 Flow）

> 目的：不只看 UI，还验证「操作后的实际产物/时长/归属/状态」是否一致。
> 每项：操作 → 原版实测结果 → 原生结果 → 结论/修复。

## 1. 视频「延长 8 秒」
| 项 | 原版 Flow | 原生 FlowClone |
|---|---|---|
| 入口 | 视频详情「延长」→ 延长 composer | 同 |
| composer | 真实胶片条（视频抽帧）+「后续步骤」+「延长 8 秒」胶囊 + 时长滑杆 + 成本「24 个 AI 点数」（720p 8s） | 已对齐：真实抽帧胶片条、预览真实帧、固定「延长 8 秒」、成本 24 点、时长条 |
| 产物 | **成片变长**：8s 视频延长后，seek 到末显示 ~0:15（≈16s）；版本数 4/4 | **修复前**：只生成 8s 片段并作为新版本（时长仍 8s） |
| 版本归属 | 同素材追加新版本（4/4、项目卡片仍 1 张、角标「4 项」） | 同素材版本 ✅（修复后 2/2、卡片「2 项」） |
| 原生修复 | — | 用 MediaExtractor + MediaMuxer 将「原视频 + 8s 续写片段」拼接为更长 MP4，作为新版本；失败自动退化为追加片段并提示 |
| 验证 | 原版：`evidence/screens/273–276` | 原生：`n279/n280/n281`（详情显示 0:04 / 0:16、2/2、卡片 2 项） |

结论：✅ 已修复（延长=真正变长，8s→16s），并保留原视频为 1/N 版本。

## 18. 取消生成的网关限制（实测记录）
- 网关 `POST /v1/jobs/{id}/cancel` 在「queued」和「running」状态下均返回 `409 JOB_NOT_CANCELABLE`（图片/视频都试过）
- 因此原生「取消生成」按钮大多数时候会得到「取消失败：任务可能已完成或不可取消」提示；原版 UI 也只在排队初期有效，此差异受网关能力限制，已在文档记录

## 19. 生成中断后的自动恢复（本轮实现）
- 原版实测（断网）：失败卡片 ⚠ + 另有卡片停在 12%，恢复网络后疑似自动继续
- 原生修复：
  - 生成失败时**保留 jobId**（不再清空）
  - 启动/回前台时自动续查：`resumePendingJobs` 覆盖「FAILED + 有 jobId」的素材，重新轮询原任务
  - 手动「重试」优先**续查原任务**（不重复扣费），原任务确认失败才重新提交
- 实测：生成中停 Server → 失败 ⚠ → 恢复 Server + 重启 App → 自动续查 `job_fabef8e80798` → 成功下载并出现在项目（`n300-auto-resume.png`）
- 说明：网关任务若已彻底失败，续查会返回 failed，此时再走重试重新提交

## 30. 深度使用中发现的真实 Bug（本轮修复）

### A. 从素材详情进入编辑/动画后，结果跑到「第一个项目」（原图"消失"错觉）
- 复现：图片详情 →「添加动画效果」（或「修改」）→ 发送 → 页面跳到 11月19 10:27 项目，原图所在项目看起来被"清空"
- 根因：composer 发送时用 `(screen as? ProjectScreen)?.id` 取项目；在 AssetScreen 上为 null → 回退 `Repo.projects.firstOrNull()`（列表第一个项目）
- 修复：项目解析顺序改为 ProjectScreen → AssetScreen(assetId) → refAsset → attach → 兜底
- 验证：修复后从 11/18 09:05 图片详情做动画，完成后仍停留该项目，原图 + 新视频卡都在（n319）

### B. 视频「修改」失败（多层原因，均已修）
1. **上传 401 不刷新**：`Gateway.upload` 无 401 refresh 重试 → token 过期后上传参考视频直接失败（服务端日志可见 POST /v1/files 401）→ 已加 refresh 重试
2. **下载超时**：网关 outputs/content 下载实测极慢（4-5MB 需 2-4 分钟），客户端 readTimeout 仅 120s → Socket closed → 任务被判失败
   - 服务端新增**输出文件本地缓存**（成功即后台下载，之后秒开）+ 直传兜底（客户端等待最长 10 分钟）
   - 客户端重试窗口 240s → **10 分钟**，并显示缓存中进度
3. **202 被当成成功**：服务端缓存未就绪时返回 202 `{"status":"caching"}`，旧客户端把 202 当 2xx 把 JSON 存成 .mp4 → 改为仅 200/201 成功，其余 202/404/409/503 重试
4. **readNBytes 崩溃**：媒体头校验用了 Android 11 不支持的 `InputStream.readNBytes`（API 33+）→ 改为手动读头
5. **媒体头校验过窄**：只认 MP4 头会误判图片（JPEG/PNG）→ 已支持 JPEG/PNG/WebP/MP4/音频魔数
6. 证据：`n328`（图片生成成功）、`n329/n330`（图片编辑同项目成功、无崩溃）；视频 E2E 因网关内容接口本轮长时间无响应未能完成最后一跳（见 §31）

## 32. 视频计费 bug：480p 实际按 720p 扣费（已修并验证）
- 现象：composer 选 480p 显示「本次生成将消耗 8 点」，但服务端每次扣 **24 点**（720p 价格）
- 根因：App 提交参数时 `quality = if (asset.quality == "360p") "480p" else "720p"` —— 480p 素材被当成 720p 提交
- 影响：余额被多扣；余额不足时出现「点 8 点却 402 失败」的诡异现象（也是用户视频修改失败的诱因之一）
- 修复：`quality = if (asset.quality == "720p") "720p" else "480p"`（生成/编辑/延长三处同源逻辑统一）
- 验证：修复后 480p 视频编辑 ledger 显示 **-8**（此前 -24），余额 100→92 ✅

## 36. 延长后「前 8 秒正常、后 8 秒无法播放」（本轮定位并修复 ✅）
- 现象：16 秒延长视频播放到第 8 秒后画面花屏/黑屏/无法解码（用户真机反馈）
- 根因（实测网关产物）：
  - 网关同一模型不同次生成的分辨率并不固定：原片 `416×752`，续写片段 `400×736`（均为所谓 480p）
  - 旧实现用 **MediaMuxer** 按第一段的视频轨格式直接写入第二段样本；第二段 SPS/分辨率不同 → 第 8 秒后解码失败
- 修复：
  - 新增 `VideoCompose`：用 **Media3 Transformer** 把两段视频先统一缩放到第一段分辨率，再整体重新编码为单一 MP4
  - 保留失败兜底（拼接失败时把续写片段作为独立版本保存并提示）
  - 同时修复：进程被杀后恢复延长任务时，恢复流程也会重新执行拼接（`extendBasePath` 持久化）
  - 交互改进：点「延长」现在对被延长的**当前版本**生效（可在右侧版本指示条切到原 8s 版本再延长）
- 验证：
  - 新片详情 **0:16**；连续截帧 0:00→0:13 全部为正常画面（`n349-extend-16s-frames-montage.jpg`）
  - ExoPlayer / MediaCodec 无任何解码错误日志
  - 证据：`n346-extend-v2-result.png`（0:04/0:16）、`n347`、`n349` 连续帧蒙太奇
